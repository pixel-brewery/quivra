# Dependency updates

Dependabot checks Cargo dependencies, npm tooling and GitHub Actions every Monday. Compatible Cargo updates share a pull request; Cargo majors receive individual pull requests under the same verification policy. GitHub Actions and npm tooling updates are grouped. TypeScript and Node type majors have no exclusions. The npm launcher has no hand-maintained runtime dependencies; packaging creates native package references from the release version.

## Enable automatic merges

The canonical public repository opts in with the Actions variable `QUIVRA_DEPENDABOT_AUTO_MERGE=true`. An active repository ruleset must protect `main` with a strict `Quality Gate` from the GitHub Actions app. Dependency automation uses the normal protected merge endpoint and has no bypass. The existing release App retains its separate authority for verified version commits, as described in the [release guide](ci-cd.md#publish-from-protected-main). The automation reads the effective status-check rule before refreshing or merging candidates; GitHub remains responsible for required reviews, thread resolution and every other active branch rule. [GitHub rulesets](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/creating-rulesets-for-a-repository) · [Actions variables](https://docs.github.com/en/actions/how-tos/write-workflows/choose-what-workflows-do/use-variables)

The privileged jobs load only the trusted `main` implementation, use the existing native workflow token, and install no pull-request dependencies or artifacts. They introduce no new App or secret. Branch refresh requires pull-request/content write permission; requesting read-only CI requires Actions write permission. A separate native-CI authorization job has only Actions write plus contents/pull-request read permission. Verification itself retains read-only repository permissions.

## Refresh and verify the exact source

Every CI or maintained release completion, the hourly schedule and an explicit controller dispatch reconcile open same-repository Dependabot pull requests. Release completion also catches version commits that intentionally skip push CI. A stale branch is updated with an expected-head guard, then polled within a fixed limit. A concurrently changed or conflicted candidate is reported individually so other updates can continue.

When the latest exact-head regular Dependabot PR CI is already successful, reconciliation calls the same separate native merge owner again. This recovers a transient skipped merge, including a temporarily unknown GitHub mergeability result, without dispatching duplicate CI. The owner repeats every current-head, base, test-merge, job, attempt and protection check; a previous green result alone cannot authorize a merge. Read-only diagnostic `workflow_dispatch` runs do not activate this resumption path and do not replace native branch-rule proof.

Existing native PR runs are retained, including approval-pending, queued, running, failed and cancelled attempts. A native-token branch refresh can produce an original `pull_request` run that requires approval. The separate authorizer can approve that original run exactly once per observed attempt; it never creates a review or check status. It requires the immutable Dependabot or GitHub Actions identity for both run actor and triggering actor. A fresh run read supplies the current attempt, so approval of the original run cannot be hidden by a newer diagnostic dispatch. The actual platform jobs must subsequently succeed.

Before any approval or diagnostic dispatch, source proof binds current protected main (M), the live own branch (B), and GitHub's live synthetic merge ref (C). M must already be an ancestor of B; C must have the exact ordered parents M/B and the same tree as B. Both CI files must be authenticated Git blobs. SHA-256 of normalized main must match the mandatory `reviewedCiSha256` in trusted-main policy, and normalized main/head bytes must match exactly. Normalization permits only a full immutable action-pin/version-comment update retaining the same action owner and path.

The fixed baseline is an explicit review decision, rather than a YAML/expression heuristic or a digest learned from GitHub/PR input. Quivra's reviewed CI grants root `contents: read`, an empty Quality Gate permission map and no custom secret inputs, environment binding or reusable job. New CI logic, additional token/secret expressions or scalar encodings require a deliberate read-only review and baseline update before dependency automation can authorize them; equality between an unreviewed main/head is insufficient. Updating an action's immutable revision retains the reviewed digest. Source, unique bot association, protection, refs and the original run/attempt are rechecked immediately before the single approval POST. An API failure is reported without blindly repeating that POST.

If no native attempt exists, an exact-source dispatch of the complete CI workflow can provide diagnostics after the same read-only source/live-ref proof. Its input `expected_head_sha` must equal the actual source checked out by CI. It cannot supply branch-rule merge proof, and existing diagnostic attempts are retained. Genuine failed checks never become successful proof through metadata or an approval decision.

Only the separate merge owner can merge. It requires:

- The latest genuine native PR run and its current attempt at the exact head. A newer diagnostic dispatch cannot shadow it. A later native attempt awaiting approval, still running or failed continues to block merging.
- All three exact platform jobs (`Verify (ubuntu-24.04)`, `Verify (macos-15)`, `Verify (windows-2025)`) and `Quality Gate`, each completed successfully with the matching run, attempt and head.
- The fixed repository IDs, workflow identity, unique actual Dependabot PR author/association, verified read-only CI source and a genuine native PR run. Its actor can also be GitHub Actions after a guarded branch refresh or a maintainer who fixes that bot branch; the same full source/job/attempt/protection proof applies. Immutable service identities are required specifically for approval, rather than excluding legitimate maintainer-authored successful CI. Head-only dispatch remains diagnostic verification.
- Current-main ancestry plus the existing synthetic merge candidate with precisely the current base and verified head as its two ordered parents.
- Fresh run, latest-run, pull-request and protected-main checks immediately before GitHub's SHA-guarded squash endpoint, followed by an actual closed/merged PR confirmation.

Forks, drafts, ambiguous associations, missing/skipped jobs, changed attempts, stale bases and unsupported protection leave the candidate open. The same policy applies to Cargo, npm and Actions changes, including majors.

## Continue CI and publication

A successful native-token merge does not itself start push-triggered workflows. The continuation therefore requests the existing main CI with `expected_head_sha` and the existing release workflow with `source_sha`. Both inputs identify the exact confirmed merge, and the source must still be current protected `main` immediately before dispatch. A newer main supersedes the request.

Both CI-event merges and resumed reconciliation merges pass their confirmed SHA to the same separate continuation job. It runs even when the event-only merge job is skipped, so scheduled recovery still receives the bound CI/release continuation. Reconciliation also recovers an interrupted continuation from the exact current-main commit association, independently of a recent-closed PR window. The simple association record only selects a candidate: a full closed/merged bot PR, matching merge SHA and fresh protected-main read must confirm it. A continuation failure remains a separately retryable workflow job rather than being hidden inside a successful reconciliation result.

The same continuation requests the existing Pages workflow only if the confirmed merge changed one of its original push paths: its workflow, product icon, site files or public configuration schemas. Pages also checks `expected_head_sha` before staging or deployment. A dependency update outside these paths requests no Pages deployment.

Existing successful, failed, cancelled or pending runs for that exact source are retained rather than dispatched twice. Retry a failed original run to reuse its verified source and artifacts. Publication remains inside the maintained release workflow, including its source checks, platform verification, existing scoped release App, atomic version commit/tag, immutable packages and GitHub Release. The controller issues no manual publication or arbitrary-ref release command.
